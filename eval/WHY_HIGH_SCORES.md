# 为什么 Fact Metrics 这么高？

## 当前结果
- **Precision: 0.9257**
- **Recall: 0.9282**
- **F1: 0.9252**

## 主要原因分析

### 1. 大部分案例都是完全匹配或接近匹配

从 20 个测试案例的分布来看：
- **完全匹配（F1=1.000）**: 4 个案例（20%）
- **接近匹配（F1>0.9）**: 12 个案例（60%）
- **中等匹配（F1 0.7-0.9）**: 4 个案例（20%）

**80% 的案例都达到了 0.9 以上的 F1 分数**，这直接拉高了平均值。

### 2. 即使有错误，影响也很小

#### 日期错误示例
```
Predicted: deadline="2025-11-13"
Ground Truth: deadline="2025-11-12"
Fact PRF: P=0.917, R=0.917, F1=0.917
```

**分析：**
- Actor, action, object 都完全匹配（5 个 token）
- 只有 deadline 不匹配（1 个 token）
- Token 集合：P 有 6 个 token，R 有 6 个 token，交集有 5 个 token
- **5/6 = 83%**，已经很高了
- 日期错误只影响 1 个 token，对整个分数影响很小

#### 对象错误示例
```
Predicted: object="budget sheet"
Ground Truth: object="Q4 budget update"
Fact PRF: P=0.909, R=0.833, F1=0.870
```

**分析：**
- "budget sheet" 和 "Q4 budget update" 有共同词 "budget"
- 根据当前逻辑，部分重叠时只添加共同 token "budget"
- 所以即使对象不匹配，token 集合中仍有 "budget"，分数不会太低

### 3. Token 集合构建逻辑的影响

#### 对象匹配逻辑
当对象有部分重叠时：
- **子集关系**（如 "slide deck" vs "slide deck review"）：添加所有 token → 视为同一对象
- **高重叠（≥85%）**：添加所有 token → 视为同一对象
- **部分重叠（<85%）**：只添加共同 token → 不会完全惩罚

**问题：**
- "budget sheet" vs "Q4 budget update" 有共同词 "budget"
- 即使对象不匹配，仍有 "budget" 这个 token 匹配
- 这导致分数不会太低

#### 日期匹配逻辑
- **日期匹配**：添加相同日期 token → 会匹配
- **日期不匹配**：添加不同日期 token → 不会匹配

**问题：**
- 日期错误只影响 1 个 token
- 如果其他字段都匹配，6 个 token 中 5 个匹配 = 83%
- 这已经是一个很高的分数了

### 4. 设计权衡

当前的设计目标是：
- ✅ **容忍格式差异**：如 "slide deck" vs "slide deck review" 视为同一对象
- ✅ **容忍命名差异**：如 "Legal Team" vs "Legal" 视为同一 actor
- ❌ **但也会导致真正的错误惩罚不够**：如日期错误、对象错误

## 具体案例统计

### 错误案例的平均分数
从 14 个有错误的案例来看：
- **平均 Precision: 0.8994**
- **平均 Recall: 0.9023**
- **平均 F1: 0.8984**

即使是有错误的案例，平均分数仍然接近 0.9。

### 常见错误类型及其影响

1. **日期错误（1 天差异）**
   - 影响：1 个 token
   - 典型分数：0.90-0.92
   - 原因：其他字段都匹配，只有 1 个 token 不匹配

2. **对象部分匹配**
   - 影响：部分 token 不匹配
   - 典型分数：0.85-0.91
   - 原因：有共同 token，不会完全惩罚

3. **Action 不匹配**
   - 影响：1 个 token
   - 典型分数：0.83-0.89
   - 原因：如果其他字段都匹配，影响有限

## 结论

Fact Metrics 高的原因：
1. **大部分案例确实匹配得很好**（80% 的案例 F1>0.9）
2. **即使有错误，影响也很小**（日期错误只影响 1 个 token）
3. **Token 集合构建逻辑容忍部分匹配**（有共同 token 就不会完全惩罚）
4. **这是设计上的权衡**：更宽松的匹配能容忍格式差异，但也会导致真正的错误惩罚不够

## 是否需要调整？

**如果认为分数太高：**
- 可以收紧对象匹配逻辑（要求更高的重叠率）
- 可以增加日期错误的惩罚（日期不匹配时降低更多分数）
- 可以要求字段级完全匹配才能获得高分

**如果认为分数合理：**
- 当前逻辑确实反映了大部分字段匹配的情况
- 部分匹配（如 "budget sheet" vs "Q4 budget update"）确实有语义相似性
- 日期错误 1 天虽然不完美，但其他字段都正确，83% 的分数是合理的
